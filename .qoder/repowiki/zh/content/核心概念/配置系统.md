- 多层配置结构：全局配置、项目配置与工作树策略的优先级

- **新增**：增强的类型安全性与配置注册表机制
- **新增**：update_check 配置键及其在更新检查中的应用

## 核心组件
- **配置注册表与类型安全**：使用 CONFIG_REGISTRY 实现强类型配置管理，支持键白名单验证和值规范化
- **配置文档模型与键访问**：支持点号分隔的嵌套键，提供读取与赋值工具函数
- **配置文件位置**：
  - 项目级：仓库根下的 .gxpm/config.json
  - 全局级：用户主目录下的 ~/.gxpm/config.json
- **工作树策略类型与来源**：
  - enforcement：required | forbidden | optional | unset
  - default：use | skip | ask
  - 来源：config-repo | config-global | user-message | agents-md | default
- **新增配置键**：update_check（布尔值，默认 true），用于控制更新检查功能
- **AGENTS.md 解析**：识别 "## gxpm config" 区块，提取键值对，支持布尔、数字与字符串

## 架构总览
配置系统采用"多层优先级 + 约定式配置 + 类型安全"的设计：
- **优先级（从高到低）**：项目配置 > 全局配置 > 用户消息（当前对话覆盖） > AGENTS.md 约定 > 默认值
- **类型安全**：通过配置注册表和类型断言确保配置键的合法性和值的正确性
- **配置注册表**：集中管理所有受支持的配置键，提供默认值、描述和规范化函数
- 项目配置与全局配置通过 JSON 文件存储，键空间支持嵌套
- 工作树策略解析贯穿上述优先级链路，并在解析后返回策略来源

## 详细组件分析

### 组件一：配置注册表与类型安全
- **设计要点**
  - 使用 CONFIG_REGISTRY 集中管理所有受支持的配置键
  - 通过 `as const` 确保配置键的字面量类型，提供编译时类型检查
  - `assertKnownConfigKey` 和 `isKnownConfigKey` 提供运行时类型断言
  - 每个配置键包含默认值、描述和规范化函数
- **配置键白名单**
  - worktree.enforcement：枚举值 required | forbidden | optional | unset
  - worktree.default：枚举值 use | skip | ask
  - update_check：布尔值，默认 true
- **规范化机制**
  - `normalizeConfigValue` 根据配置键选择相应的规范化函数
  - `normalizeBoolean` 确保 update_check 只接受布尔值
  - `normalizeEnum` 验证枚举类型的值

### 组件三：工作树策略解析
- **解析优先级链路**
  1) 项目配置（repo）：若存在 worktree.enforcement，则直接返回，default 若缺失则回退为 "ask"
  2) 用户消息（userMessage）：若传入 enforcement，则覆盖 AGENTS.md
  3) AGENTS.md：解析 "## gxpm config" 区块，提取 worktree.* 键
  4) 默认：enforcement="optional"，default="ask"，source="default"
- **输入参数**
  - root：仓库根（默认当前工作目录）
  - home：用户主目录（默认 OS home）
  - userMessage：当前对话中用户声明的工作树偏好
  - agentsMdContent：显式传入 AGENTS.md 内容（用于测试）

## 性能考量
- 配置读取为轻量级文件 I/O，解析复杂度与键深度线性相关
- 配置注册表使用常量映射，查找时间为 O(1)
- 建议：
  - 避免频繁重复读取同一配置
  - 在批量场景下缓存已解析的配置文档
  - 控制嵌套键深度，保持配置简洁可维护
  - 利用配置注册表的类型检查减少运行时错误

## 故障排查指南
- **键不存在**
  - 表现：config get 返回 <unset>，source 为 unset
  - 处理：确认键名正确（包含点号）、作用域（repo/global）
- **未知配置键**
  - 表现：setConfigValue 抛出 "Unknown config key" 错误
  - 处理：检查配置键是否在 CONFIG_REGISTRY 中，确认拼写正确
- **值类型错误**
  - 表现：update_check 设置为非布尔值时抛错
  - 处理：确保 update_check 只设置为 true 或 false
- **JSON 解析错误**
  - 表现：读取配置时捕获异常并返回空文档
  - 处理：检查 .gxpm/config.json 语法，确保为合法 JSON
- **AGENTS.md 未生效**
  - 表现：策略未按预期
  - 处理：确认标题为 "## gxpm config"，键符合 worktree.*，值可被规范化
- **优先级不符合预期**
  - 表现：repo 配置未覆盖 global
  - 处理：检查 repo 配置文件是否存在且键正确；测试用例可参考

## 结论
gxpm 的配置系统以清晰的多层优先级、约定式配置和强类型安全为核心，既保证了灵活性（可通过 AGENTS.md 约定工作流），又提供了强约束（项目配置可覆盖全局）。通过配置注册表机制，系统实现了编译时和运行时的双重类型检查，确保配置的正确性和一致性。新增的 update_check 配置键进一步增强了系统的可配置性，为用户提供更精细的控制选项。通过 CLI 子命令与核心 API，用户可以便捷地读取、设置与诊断配置。

### 配置加载与覆盖规则
- **加载顺序**
  1) 项目配置（.gxpm/config.json）
  2) 全局配置（~/.gxpm/config.json）
  3) 用户消息（当前对话覆盖）

  - 项目配置覆盖全局配置

  - AGENTS.md 覆盖默认值
- **类型安全规则**
  - 所有配置键必须在 CONFIG_REGISTRY 中定义
  - 值必须通过相应的规范化函数验证
  - 未知配置键将被拒绝
